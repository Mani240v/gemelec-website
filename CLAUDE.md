# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Static marketing website for Gemelec Electrical Services (Sydney electrician). Plain HTML/CSS/JS with Vercel serverless functions for lead/job capture. No framework, no build step, no bundler. The frontend has no dependencies at all (Swiper comes from a CDN). The API functions have exactly two: `@vercel/blob` (added 2026-09-01, job-photo storage) and `@vercel/functions` (added 2026-09-07, `waitUntil` so the AI costing and the alerts run after the response instead of making the customer wait for them). Everything else there is Node built-ins, including the hand-signed Google OAuth JWT. Treat that count as a budget: reach for a built-in before a package. Git remote is `github.com/Mani240v/gemelec-website`, deployed on Vercel.

## How to work with Mani

- Talking to Mani: he likes seeing the nuts and bolts, so keep the technical detail,
  the evidence and the reasoning. Then finish anything non-trivial with a short
  plain-English wrap-up, pitched at a 40-year-old with general IT knowledge: what
  changed, what it means for him, and what he needs to do next (often nothing). No
  jargon in that part, and no file paths, commands or code unless he has to type
  them himself.

## Commands

```bash
npm run dev         # npx serve . -p 3456 — static preview, does NOT run /api/job-request
npm run dev:vercel  # vercel dev on 3456 — required to exercise the job-request form endpoint
```

There is no build, lint, or test step. "Editing" is editing HTML/CSS/JS directly; "verifying" is loading the page. Use `npm run dev:vercel` whenever a change touches `api/job-request.js`, either form, or anything that posts to `/api/job-request`.

## Architecture

### No templating — page chrome is duplicated into every file
There are ~38 standalone HTML files and **no shared header/nav/footer partial**. The `<head>`, top nav, and footer are hand-copied into each page. A change to any shared element (nav links, footer, phone number, logo, a new `<head>` tag) must be applied to **every** HTML file, not one. Active nav state is hard-coded per page via `class="active"`, not computed by JS. Treat any "site-wide" copy or markup change as a multi-file find-and-replace.

### Page taxonomy
- Root pages: `index`, `services`, `about`, `contact`, `blog`, `privacy-policy`.
- `tech.html` — the **field portal** (`/tech`), added 2026-09-01. Staff-only, `noindex`, installable to a phone home screen via `manifest.webmanifest` + `sw.js`. A technician on site enters the customer, dictates the description with the phone keyboard's mic, attaches photos, and posts to the **same** `/api/job-request` as the customer form — one pipeline, one price book, one dashboard. Gated by `api/tech-auth.js`, which checks `TECH_ACCESS_CODE` if set and otherwise falls back to `DASHBOARD_PASSWORD` (Mani's techs are trusted with pricing; the separate code exists for subcontractors). The technician's name rides in the existing `source` column as `On site — <name>`, so no `HEADERS` change was needed; the dashboard renders that as a badge whenever `source !== 'website'`.
- **Add to home screen (2026-09-28):** `manifest.webmanifest` carries 192/512 (+ maskable) icons at `/images/tech-icon-*.png` (Android won't offer install without them), and `tech.html` uses `tech-icon-180.png` as its apple-touch-icon. `js/tech-portal.js` shows a `#tech-install` box in a browser tab: a one-tap Install button where Chrome fires `beforeinstallprompt`, the Share-menu steps on iPhone (Safari has no install API), the browser-menu steps elsewhere on touch devices. It never shows when already running installed, and stays gone once dismissed (`gemelec_tech_install_dismissed`).
- The service worker handles only the paths in its `SHELL` list (the `/tech` and `/job-requests` pages and their assets), network-first, and never `/api/`. Its scope is `/`, so until 2026-09-28 it intercepted and cached the whole marketing site on staff phones and served `/tech` for any failed request; the fetch handler now returns early for anything outside `SHELL`. Bump `CACHE` whenever `SHELL` changes. It does **not** queue offline submissions — see the comment in `sw.js` before adding that.
- `electrician/<suburb>.html` — 24 suburb landing pages (Matraville, Bondi, Coogee, etc.). These share component blocks: breadcrumb, suburb hero, area grid, FAQ, related services, nearby suburbs.
- `services/<slug>.html` — 6 service detail pages (emergency, switchboard upgrades, EV charger, lighting, commercial, security). Share: service detail hero, included grid, process steps, FAQ, related services.

Adding a page means also updating `sitemap.xml`, the nav block in every page (if it belongs in nav), and `llms.txt`.

### Job request pipeline (single pipeline for both `/contact` and `/job-request`)
Both `contact.html` (`form#job-request-form`) and `job-request.html` (same form id) share `js/job-request.js` for photo compression, address autocomplete, and submit handling → `POST /api/job-request` → `api/job-request.js` appends a row to Google Sheets, best-effort uploads photos to Drive, best-effort drafts an AI rough costing (`api/_lib/anthropic.js`), and fires best-effort email (Resend) + WhatsApp (Twilio) alerts. There is no separate lead-capture pipeline — `api/lead.js` and the n8n webhook it used were retired in favor of this one.

- `api/job-request.js` is a Vercel serverless function. It mints a Google OAuth token by hand-signing a JWT (RS256 via `node:crypto`) — there is no `googleapis` dependency. Sheet target comes from env vars (see `VERCEL_SETUP.md`).

#### Job photos — Vercel Blob, private, purged after 14 days
Photos used to go to Google Drive. That never worked: a bare service account has no Drive storage quota, so every upload failed, and fixing it needed a Workspace shared drive or domain-wide delegation. Replaced 2026-09-01 with Vercel Blob. `api/_lib/google-drive.js` is gone; do not reintroduce it.

- **The sheet's `photo_links` column holds blob PATHNAMES now, not URLs.** Private blobs are not fetchable by URL, so a URL there would look like a working link and never be one. Rows written before 2026-09-01 may hold Drive URLs; the dashboard tells them apart by the `job-photos/` prefix rather than migrating them.
- **Everything is written under the `job-photos/` prefix**, and both the purge and the read path are scoped to it. The purge lists only that prefix, so a blob another feature puts in this store cannot be deleted by it; `getPhoto` refuses anything outside it, so the dashboard password is not a key to the whole store. Keep both scopes if you touch `api/_lib/photo-store.js`.
- **The email attachment is the archive, not the blob.** Blob holds photos for `PHOTO_RETENTION_DAYS` (default 14, floor 1, ceiling 3650); the alert email carries them until someone deletes it. `api/job-request.js` attaches them on *every* submission — it used to skip attachments when an upload succeeded, and reinstating that would make the expiring copy the only copy.
- **Retention promise (privacy policy, 2026-09-28): enquiries that don't go ahead are deleted after 3 months.** Nothing automates that yet: the sheet rows and the alert emails both have to be cleared by hand (or by a purge job someone builds). If you change what is collected or kept, change `privacy-policy.html` in the same commit.
- **`api/job-photo.js` is the only way the bytes come out**, gated like the rest of the dashboard (staff cookie or `DASHBOARD_PASSWORD` header). An `<img src>` cannot send the header, so `js/job-requests-dashboard.js` fetches each photo and hands the `<img>` an object URL.
- **`api/purge-photos.js` runs daily from the `crons` block in `vercel.json`** (16:00 UTC = ~2am Sydney) and requires `CRON_SECRET`. **`CRON_SECRET` was missing until 2026-09-29**, so every nightly run was refused (401, fail-closed) and no photo was ever purged from 2026-09-01 on; the first run after it was added clears the whole backlog older than 14 days. Env vars only reach a deployment built after they are saved, so after adding or changing one, redeploy. If purges ever stop again, check this variable first.
- Honeypot field: `gx_check` (label "Leave this field empty"). If filled, the function returns `200 ok` without writing (silent bot drop). It was `company_website` until 2026-09-28 and was renamed because browser autofill reads "company"/"website" as fields to fill, which silently dropped real leads; the server still drops on either name so a stale cached page keeps its trap. Never give the trap a name, id or label an autofill heuristic would recognise.
- Required fields: `full_name` (sent as `first_name`/`last_name` from the form, combined client-side), `phone`, `description`. Photos are optional (up to 5) — a submission with none still gets an AI summary attempt from the description text alone.
- The `HEADERS` array in `api/job-request.js` defines the exact sheet column order. **To add a form field you must touch three places**: the form HTML (both `contact.html` and `job-request.html` if it applies to both), the payload object in `js/job-request.js`, and both `HEADERS` + the `row` object in `api/job-request.js`.
- Dashboard at `/job-requests` (password-gated, see `DASHBOARD_PASSWORD`) is where every submission — general enquiry or job-with-photos — gets reviewed, AI costing edited, and status tracked.

#### Staff sign-in — one cookie for `/tech` and `/job-requests` (2026-09-29)
Mani was re-typing the password constantly: the dashboard kept it in sessionStorage (every new tab, including every alert's "Review:" link, asked again) and iPhone Safari wipes localStorage after ~7 days unvisited. Both pages now sign in through `api/staff-session.js` (GET check + refresh, POST sign in / rename, DELETE sign out), which sets `gx_staff`: **HttpOnly, Secure, SameSite=Strict, 180 days, refreshed on use**. The token (`api/_lib/staff-session.js`) is `v1.expiry.role.name.hmac`. The HMAC key is an HMAC under a **server-only secret** (`STAFF_SESSION_SECRET` if set, else `GOOGLE_PRIVATE_KEY`, which every deployment already has) over the current `DASHBOARD_PASSWORD` + `TECH_ACCESS_CODE`. Never key it from the passwords alone: a pre-release review caught that this turns every cookie into an offline password-cracking oracle (a subcontractor on the tech code could crack the office password from their own cookie). Because the passwords are mixed in, **changing either password signs every device out** — that is the lost-phone lever, keep it. Rotating the secret does the same. The cookie is only honoured when `Sec-Fetch-Site` is `same-origin` (or absent, for old browsers), since an ambient cookie now reaches the delete/update endpoints that a custom header used to shield. A dashboard sign-in sends `scope: 'office'` so a tech code is refused there instead of downgrading the device's cookie, and a sign-in without a name keeps the name already on the cookie. Roles: `office` = `DASHBOARD_PASSWORD` (dashboard + portal), `tech` = a separate `TECH_ACCESS_CODE` (portal only). `isAuthorized` accepts an `office` cookie first, then the old `X-Dashboard-Auth` header (kept so tabs open from before still work). The password is no longer stored in any JS-readable storage; the portal's old `gemelec_tech_code` is read once to mint a cookie, then deleted. `api/tech-auth.js` stays for phones on the old script and also sets the cookie. The API calls need no wiring: same-origin `fetch` sends the cookie.

#### New-enquiry push notifications (2026-09-29)
Until this, a website enquiry reached Mani only by email, and only after the AI costing (up to a minute). **The WhatsApp alert in `api/_lib/whatsapp.js` has never been live: there are no `TWILIO_*` env vars**, so `sendWhatsAppNotification` quietly returns false. Staff devices can now opt in to Web Push from a box on `/tech` and `/job-requests` (`js/staff-push.js`, office sign-in required via `api/push-subscribe.js`). `api/job-request.js` sends the push (`enquiryPush`) for `source === 'website'` only, **first thing in the post-response work, before the costing**, and on the sheet-failure path too. `api/_lib/web-push.js` implements VAPID (RFC 8292) and aes128gcm payload encryption (RFC 8291) on `node:crypto`, no `web-push` package. The VAPID key pair is **derived** from the same server secret as the staff cookie (label `gemelec-vapid-v1`), so there is no key to configure; rotating the secret invalidates every subscription and `staff-push.js` resubscribes when it sees the public key change. Subscriptions are private blobs under `push-subs/<sha256(endpoint)>.json`; 404/410 from a push service deletes one. Endpoints are allow-listed to the real push services (the server POSTs to them). `sw.js` shows every push (iPhone revokes the permission from a web app that receives silent pushes) and opens `/job-requests` on tap. iPhone needs iOS 16.4+ and the portal added to the home screen. Nine → ten serverless functions (Hobby limit is 12).

### CSS
Single file `css/style.css` (~2350 lines), organized by `/* ─── Section ─── */` comment banners. New component groups are appended at the bottom under a dated comment (e.g. `/* === ADDED 2026-05-14 ... === */`) rather than edited inline. Follow that convention. Client brand fonts are **Barlow Condensed + DM Sans** (this is Gemelec's brand, not switchflow's — do not apply switchflow brand fonts/colours here).

### Deployment config
`vercel.json` sets `cleanUrls: true` (URLs are extensionless: `/about`, `/services/emergency-electrician`), plus security headers, a 1-year immutable cache on `/images`, and `max-age=0, must-revalidate` on `/css` and `/js` (changed 2026-09-01, so a CSS/JS edit reaches everyone on the next load). Because of that the `?v=` strings on stylesheet and script tags are no longer what keeps files fresh, and several are stale; do not switch `/css` or `/js` back to immutable unless every reference gets a reliable per-change version.
- **`.vercelignore` keeps internal docs off the live site.** Vercel deploys every file in the repo by default, so `/CLAUDE.md`, `/REVIEWS.md` and `/VERCEL_SETUP.md` were publicly readable on www.gemelec.com.au until 2026-09-28. Any new internal doc or notes file must be added to `.vercelignore`. Never list `package.json`/`package-lock.json` there — the API functions need them.
- **`404.html`** at the root is Vercel's not-found page, served at arbitrary depths (`/electrician/Bondi`), so every link and asset in it is root-absolute. **`electrician.html`** is the service-areas hub at `/electrician`, which the suburb pages' breadcrumbs point to.

## Conventions and gotchas

- **Internal links are mixed style.** Root pages link with absolute extensionless paths (`/about`, `/services`). Suburb pages link to parents/siblings with relative `.html` (`../about.html`, `coogee.html`) and to services with absolute extensionless (`/services/emergency-electrician`). `cleanUrls` makes all of these resolve. Match the style already used in the file you are editing rather than normalizing.
- **Canonical domain is `https://www.gemelec.com.au`.** Every page's `canonical`, `og:url`, JSON-LD `url`, plus `sitemap.xml`, `robots.txt`, and `llms.txt` were migrated off the old `gemelec-website.netlify.app` domain. Keep new pages consistent with this.
- **Two analytics systems run side by side.** Vercel Web Analytics (`/_vercel/insights/script.js`, loaded near `</body>`) and Google Analytics 4 (`G-LJK30G1W7Z`, gtag snippet as the first thing inside `<head>`). GA4 was added 2026-09-07; before that the only gtag on the site was a `G-XXXXXXXXXX` placeholder on `job-request.html` alone. The GA4 tag is on all 38 public pages and deliberately **not** on `tech.html` or `job-requests.html` — those are staff tools, and tagging them would file Mani's own team's activity as site traffic. A new page needs the snippet copied in like the rest of the chrome.
- **Leads are measured by one event, `generate_lead`, split by a `method` parameter** (`phone`, `whatsapp`, `form`) — see the block at the bottom of `js/main.js`. Phone and WhatsApp are counted because the form is the *minority* channel here: 187 `tel:` links and 40 `wa.me` links against one form. A new contact channel should reuse `generate_lead` with a new `method` rather than inventing an event, so the single key event configured in GA4 keeps covering everything. The click handler is delegated from `document`, so new `tel:`/`wa.me` links anywhere need no wiring. **WeChat** (added 2026-09-28) is `method: 'wechat'`: WeChat has no click-to-chat URL, so any element with `data-wechat` opens a QR-code dialog built by `js/main.js` (image `/images/wechat-qr.jpg`), and its `href` points at that image as the no-JS fallback. It is on the contact and job-request heroes, the contact sidebar, and every public footer. The dialog also shows the WeChat ID `GEMELEC` (a custom ID Mani set on 2026-09-28; the system `wxid_` it replaced isn't searchable in WeChat) with a copy button. If he ever changes the ID or resets his QR code, update `WECHAT_ID` in `js/main.js`, the contact-page WeChat card, and `/images/wechat-qr.jpg` (new file name, since `/images` is cached immutably). `js/main.js` is loaded by exactly the 38 public pages and neither staff page, which is why the tracking has the right footprint for free.
- **The form conversion is gated on a one-shot `gx_pending_lead` sessionStorage token** written by `js/job-request.js` after a successful POST and consumed on arrival at `/thank-you`. Do not "simplify" this to a sticky already-counted flag: that never clears, so a customer's second enquiry in the same session goes uncounted. Storage errors fail *open* on read and are swallowed on write — losing a real lead is worse than counting one twice, and it must never break the redirect.
- **Adding or removing a tracker means editing `privacy-policy.html`.** Its "Cookies and analytics" section names Google Analytics specifically and the "Who we share it with" list names Google as the provider. That page was factually wrong for as long as it took to notice — it claimed no third-party tracking. Update it in the same commit as any tracking change, and bump its `Last updated` date.
- **Copy accuracy matters.** The owner is "Mani" (Emmanuel Gemelas), not "Manny" — a prior pass replaced Manny→Mani site-wide. The one intentional exception is the verbatim G A Tigani Google review, which keeps the original "Manny" spelling. Phone `0498 351 351` and the NSW licence numbers in `llms.txt`/schema are real and load-bearing; do not invent or alter them.
- **JSON-LD schema** (`ElectricalContractor`) is embedded per page in `<head>`. Keep NAP (name/address/phone), licences, and service lists in sync with `llms.txt` and `about.html` when any of them change.
